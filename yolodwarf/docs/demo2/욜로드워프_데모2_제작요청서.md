# 욜로드워프 데모 2.0 제작 요청서

> 2026-11-24. Claude Code에게 넘기는 문서다. **데모 1.0의 저장소 위에 2.0을 올린다.**
> 이 문서는 무엇을 어떤 순서로 만들지와 끝났다고 볼 기준을 적는다. 규칙 자체는 규칙 문서에 있다.
> 수치는 모두 임시다. 사람이 해 본 뒤에 고친다. 그래서 수치는 한곳(데이터 파일)에서만 읽게 만든다.

## 2. 무엇을 만드는가

욜로드워프는 혼자 하는 로그라이크 타이쿤이다. 고리 모양 거리에 건물을 짓고, 손님인 드워프가 그 거리를 돌며 매장마다 돈을 낸다. 번 돈이 곧 점수다.

데모 1.0은 12칸 보드에서 웨이브 다섯을 하는 한 스테이지였다. **데모 2.0은 스테이지 다섯(웨이브 스물다섯)을 잇는 한 런이다.** 보드가 스테이지마다 커지고(8, 12, 16, 20, 24칸), 건물이 46채에서 95채로 늘고, 건물 업그레이드와 드워프의 특성이 들어온다. 베타 테스트에 쓸 수준으로 만든다.

바뀌는 것의 전체 목록은 규칙 문서의 0절에 표로 있다. 거기에 적히지 않은 것은 1.0과 같다.

## 3. 시작하기 전에

1. **저장소를 먼저 읽는다.** 1.0의 계산 엔진, 데이터를 읽는 곳, 검증 사례를 돌리는 테스트, 화면의 구조가 어디에 있는지 파악한다. 2.0은 그 구조를 이어 쓴다. 새 틀을 들이지 않는다.
2. **규칙 문서를 끝까지 읽는다.** 0절(바뀌는 것)부터 본다.
3. 참고 엔진을 돌려 221개가 통과하는 것을 확인한다.
4. 1.0의 데이터 파일, 참고 엔진, 검증 사례는 2.0의 것으로 바꾼다. 1.0의 검증 사례는 규칙이 바뀌어서 더는 맞지 않는다(만족도가 0 아래로 내려가고, 성장 지원이 추가 바퀴에서만 자라고, 피로가 생겼다). 지운다.

## 4. 일의 순서

단계마다 게임이 돌아가는 상태로 끝낸다. 단계가 끝날 때마다 커밋한다.

### 단계 A. 데이터와 계산

- `yolodwarf2_data.json`을 읽는다. 건물의 효과, 상수, 스테이지의 값은 모두 여기서 읽는다. 코드에 숫자를 적지 않는다.
- 계산 엔진을 규칙 문서 6~10절에 맞게 고친다. 참고 엔진을 그대로 가져다 써도 되고, 1.0의 엔진을 고쳐도 된다. 판정은 검증 사례다.
- 검증 사례 221개를 테스트로 넣는다. **221개가 모두 통과해야 다음 단계로 간다.**
- 1.0의 엔진에서 반드시 바뀌는 곳: 업종 여덟, 피로와 휴식의 변환, 만족도가 0 아래로 내려감, 단골(좋아하는 드워프에게 스택을 더 준다), 문턱에서 매출 ×2, 스택을 모두 소모하고 읽기, ★(매출 ×2씩), 특성(바퀴를 시작할 때의 스택, 기본 3바퀴), 성장 지원이 추가 바퀴에서만 자람, 자라는 매출 배율은 건물마다 따로 갖고 서로 곱함, 지원 건물 43채의 효과.

### 단계 B. 런의 뼈대

- 스테이지 다섯을 잇는다. 스테이지가 바뀌면 보드, ★, 잠근 후보, 새로고침의 비용이 처음으로 돌아간다. **자금은 남는다.**
- 보드의 칸 수는 스테이지마다 8, 12, 16, 20, 24다.
- 목표 25개(데이터 파일의 `stages[].targets`)로 판정한다. 자금이 목표 이상이면 통과다.
- 다섯째 스테이지의 다섯째 웨이브를 통과하면 클리어 화면, 모자라면 끝 화면이다.

### 단계 C. 정비

- 후보를 등급의 확률로 뽑는다(규칙 3.3절). 후보 수와 짓는 수는 스테이지마다 다르다.
- 철거를 넣는다.
- 새로고침의 비용을 바꾼다(규칙 11절).
- 업그레이드를 넣는다(규칙 10절). 매장마다 지난 웨이브의 매출을 적어 두어야 한다. 자리 바꾸기를 해도 ★과 매출 기록이 건물을 따라간다.
- 용어가 바뀌었다. 얼리기는 잠금, 제거는 철거다.

### 단계 D. 드워프

- 풀 90마리(데이터 파일의 `dwarves`)에서 스테이지마다 30마리를 뽑는다(규칙 5.2절의 무게).
- 30마리 가운데 10마리에 특성을 붙인다(다섯 가지를 두 마리씩).
- 덱 화면에 인기 업종 둘과 비인기 업종 하나를 보여 준다. 드워프 카드에 특성 배지를 단다.

### 단계 E. 화면과 글

- 보드를 둥근 네모 트랙으로 그린다(규칙 4절). 칸 수가 바뀌어도 큰 틀은 네모다.
- 규칙 문서 13절과 텍스트 v3의 6절에 적힌 것을 보여 준다.
- **모든 글을 텍스트 v3으로 바꾼다.** 건물의 문구는 데이터 파일의 `text`에 있다. 버튼과 안내의 문구는 텍스트 v3의 8절에 있다. 5절이 용어 사전이다.
- 속도: 배속 버튼(1배, 2배, 4배)과 결과만 보는 버튼을 넣는다. 24칸은 한 웨이브가 360걸음쯤이라 이것이 없으면 한 런을 끝까지 하기 어렵다.

### 단계 F. 시험용 스위치와 기록

- 규칙 문서 14절의 스위치 여섯 개.
- 끝 화면에 이번 런의 최종 자금, 닿은 스테이지와 웨이브, 한 번에 올린 최고 매출, 가장 많이 돈 바퀴 수. 역대 최고 기록은 1.0과 같은 방식으로 남긴다.

## 5. 계산의 기준

### 5.1 검증 사례의 꼴

사례 하나는 보드 하나에 드워프를 한 마리에서 세 마리까지 차례로 보낸 웨이브다.

| 필드 | 뜻 |
|---|---|
| `board` | 0번 칸(입구)부터의 건물 id. 빈 칸은 null |
| `levels` | 칸마다의 ★ 수 |
| `wave` | 보내는 순서대로의 드워프. `likes`(좋아하는 업종 둘), `dislike`(싫어하는 업종 하나), `trait`(특성의 id나 null) |
| `expected.perDwarf` | 드워프마다의 매출 합(`sales`), 돈 바퀴 수(`laps`), 추가 바퀴 수(`extraLaps`) |
| `expected.waveSales` | 웨이브의 매출 합 |
| `expected.salesByTile` | 웨이브 동안 칸마다 들어온 매출. 2호점에서 올린 것은 본점의 칸에 더한다 |
| `expected.topTile` | 요금이 가장 높은 매장의 칸 |
| `expected.feeByTile`, `multByTile` | 웨이브를 시작할 때 매장마다의 요금과 걸린 ×. 자라는 것은 뺀 값이다. 지원 건물과 빈 칸은 null |

묶음(`group`)은 일곱이다. 매장마다 하나(shop, 52), 지원 건물마다 하나(support, 43), 발전소 옆의 지원 건물(power_plant, 42), 보드 크기마다의 무작위 웨이브(random, 50), 축제 본부와 방송국이 함께 있는 보드(growth와 growth_long, 12씩), 회전문이 걸린 휴식의 매장(rest_again, 10).

틀린 사례가 나오면 `feeByTile`과 `multByTile`부터 본다. 여기가 다르면 지원 건물을 읽는 곳이 틀린 것이고, 여기가 같으면 드워프가 도는 곳이 틀린 것이다.

### 5.2 검증 사례가 다루지 않는 것

난수가 끼거나 정비의 흐름인 것은 사례에 없다. 테스트를 직접 쓴다.

| 무엇 | 확인할 것 |
|---|---|
| 후보 뽑기 | 많이 뽑았을 때 매장 62%, 일반 23%, 고급 13%, 희귀 2% 언저리인가. 보드에 지은 지원 건물과 지금 후보에 있는 지원 건물이 다시 나오지 않는가 |
| 덱 | 30마리가 모두 다른가. 특성이 다섯 가지 두 마리씩 10마리인가. 인기 업종을 좋아하는 드워프가 비인기 업종을 좋아하는 드워프보다 뚜렷이 많은가 |
| 업그레이드 | 비용이 max(10, 지난 웨이브 매출 × 2)인가. 정비마다 한 번인가. 이번 정비에 지은 매장은 못 올리는가. ★ 셋에서 멈추는가. 지원 건물은 못 올리는가. 자리를 바꿔도 ★과 매출 기록이 따라가는가. 철거하면 사라지는가 |
| 새로고침 | 스테이지 1에서 5, 10, 20으로 오르는가. 웨이브가 넘어가도 내려가지 않는가. 스테이지 2에서 10으로 시작하는가. 잠근 후보가 남는가 |
| 스테이지 전환 | 자금이 남는가. 보드, ★, 잠근 후보가 사라지는가. 새 덱이 뽑히는가 |
| 판정 | 자금이 목표와 같으면 통과인가. 새로고침과 업그레이드에 쓴 만큼 빠지는가 |
| 웨이브 끝 | 성장 지원이 자란 것이 처음으로 돌아가는가 |

참고 엔진에 `upgradeCost`와 `refreshCost`가 있다.

## 6. 글

- 문체와 표기는 텍스트 v3의 3절을 따른다. +는 더하기에만, ×는 곱에만, ★는 업그레이드 단계에만 쓴다. %는 쓰지 않는다.
- 문구의 `[운동]`, `[식당]` 같은 대괄호는 그 업종의 아이콘으로 바꿔 그린다.
- 성장 지원 네 채의 문구는 "(지금 +0)", "(지금 ×1)"로 끝난다. 이 꼬리는 화면이 지금 값으로 바꿔 그린다. 추가 바퀴마다 바뀐다.
- 옛 말이 화면에 남지 않게 한다: 낸 돈, 가진 돈, 장사 건물, 종류, 상점, 허기짐, 취함, 피곤함, 배부름, 받지 않는다, 얼리기, 제거. 텍스트 v3의 5.4절이 쓰지 않는 말의 목록이다.
- 건물과 드워프의 이름은 데이터 파일의 `name`이다. `oldName`은 옛 문서와 맞춰 볼 때만 쓴다. 화면에 내지 않는다.

## 7. 하지 않을 것

- **수치를 고치지 않는다.** 목표, 요금, 확률이 이상해 보여도 그대로 둔다. 사람이 해 보고 고친다. 이상한 점은 따로 적어서 알린다.
- **규칙을 채우지 않는다.** 규칙 문서에 없는 경우가 나오면 참고 엔진이 하는 대로 한다. 참고 엔진에도 없으면 가장 단순한 쪽으로 만들고, 무엇을 그렇게 정했는지 목록으로 남긴다.
- 규칙 문서 16절의 것(지원 건물의 업그레이드, 아이템, 무한 모드, 처음 하는 사람을 위한 안내 들)은 만들지 않는다.
- 그림과 소리를 새로 크게 벌이지 않는다. 1.0의 꼴을 이어 쓰고, 새 건물 49채와 새 업종(카페)은 같은 방식으로 채운다.

## 9. 알아 둘 것

- **자금이 런 동안 남는다.** 목표도 런 전체에서 이어 오른다. 앞 스테이지에서 크게 번 판은 뒤 스테이지의 목표를 이미 넘은 채로 들어간다. 버그가 아니다.
- **같은 낱말이 다른 건물을 가리키던 때가 있다.** 옛 문서에서 "디저트 카페", "로스터리", "기획사", "발전소"는 지금과 다른 건물이다. 옛 문서의 이름으로 건물을 찾지 않는다. 데이터 파일의 id와 `oldName`으로 찾는다.
- 숫자가 크게 자란다. 24칸에서 잘 풀린 판은 한 번의 매출이 수만, 런의 자금이 수십만을 넘는다. 세 자리마다 쉼표를 찍고, 칸이 좁으면 줄여 적는다(12.3만).
- 곱하는 수가 모두 0.5의 배수(1.5, 2, 2.5, 3)라서 부동소수점으로도 값이 정확하다. 소수는 매출을 셈할 때 마지막에 한 번만 버린다.
